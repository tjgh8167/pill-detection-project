# Model Selection

## 프로젝트 조건 분석

| 조건 | 분석 |
| --- | --- |
| 알약 이름(클래스) 검출 | 외형이 비슷한 객체가 많아 세밀한 분류 능력이 필요 |
| 바운딩 박스 검출 | 객체를 얼마나 정확하게 감싸는지가 성능에 직접적으로 영향 |
| mAP@[0.75:0.95] | IoU 0.75 이상부터 평가되므로 박스 정밀도가 중요 |
| 최대 4개 객체 | 한 이미지의 객체 수가 적어 속도보다 정확도와 안정성을 우선 고려 |

## 후보 모델 비교

### YOLOv11

Ultralytics에서 제공하는 one-stage detector입니다.

장점:

- `get_model()` 구현이 단순해 빠르게 baseline을 만들 수 있음
- 레퍼런스와 커뮤니티 자료가 많아 디버깅 부담이 낮음
- pretrained weight를 활용해 빠르게 fine-tuning 가능
- `n`, `s`, `m`, `l`, `x` 등 모델 크기를 선택할 수 있음
- Experimentation Lead와 실험 조건을 공유하고 반복하기 좋은 구조

단점:

- Transformer 계열보다 bbox 정밀도가 낮을 수 있음
- 외형이 비슷한 알약을 구분하는 데 한계가 있을 수 있음

### RT-DETR

Baidu에서 발표한 Transformer 기반 detector입니다.

장점:

- bbox 정밀도가 높아 엄격한 IoU 기준에서 강점이 있음
- 외형이 비슷한 객체 구별에 유리할 수 있음
- NMS 없이 end-to-end 검출 가능

단점:

- YOLOv11보다 구현 복잡도가 높음
- 학습과 추론 시간이 더 오래 걸림
- GPU 메모리 요구량이 큼
- 프로젝트 기간 안에서 디버깅 리스크가 있음

### Faster R-CNN

Two-stage detector로, 정확도 중심의 객체 탐지 모델입니다.

장점:

- 두 단계 검출 구조로 정확도가 높음
- torchvision에 내장되어 접근성이 좋음
- 소형 객체 검출에 강점이 있음

단점:

- YOLO 계열보다 속도가 느림
- 학습 설정이 비교적 복잡함
- 단기 프로젝트에서 실험 반복 속도가 떨어질 수 있음
- 최신 모델 대비 성능상 한계가 있음

### SSD

One-stage detector로 실시간 처리에 강점이 있는 모델입니다.

장점:

- 속도가 빠름
- 다양한 크기의 객체를 동시에 탐지할 수 있음
- 구조가 단순해 구현 부담이 낮음

단점:

- 정밀도가 낮아 mAP@0.75 이상 기준에 불리함
- 작은 객체 검출 성능이 약함
- 최신 YOLO 계열 대비 성능 차이가 큼

### YOLOv1 / YOLOv2 / YOLOv3

YOLO 계열의 초기 버전들입니다.

장점:

- 구조가 비교적 단순해 객체 탐지 원리를 이해하기 좋음
- YOLOv2부터 anchor box를 도입했고, YOLOv3는 multi-scale detection으로 소형 객체 탐지를 개선함

단점:

- 최신 모델 대비 성능 차이가 큼
- 작은 객체나 인접 객체 검출에서 한계가 있음
- mAP@0.75 이상 기준에서는 최신 모델에 비해 불리함

### YOLOv12 / YOLO26

최신 계열 모델입니다.

장점:

- 최신 아키텍처를 적용해 벤치마크 성능이 높음
- Attention, NMS-free 추론 등 최신 구조를 활용할 수 있음

단점:

- 레퍼런스와 튜토리얼이 부족함
- 팀 프로젝트에서 디버깅 난이도가 높음
- 안정성이 충분히 검증되지 않았다고 판단함
- 3주 프로젝트 일정에서는 리스크가 큼

## 진행 전략

1. YOLOv11 Medium으로 baseline pipeline을 먼저 완성
2. baseline 성능을 확인하면서 학습 조건과 데이터 처리 흐름을 조정
3. 성능이 부족할 경우 RT-DETR 교체 또는 YOLOv11 Large 업그레이드를 검토

## 최종 선택

최종 모델은 **YOLOv11 Medium**으로 결정했습니다.

RT-DETR은 bbox 정밀도 측면에서 매력적인 후보였지만, 구현 복잡도와 실험 시간, GPU 메모리 부담이 컸습니다. 반면 YOLOv11 Medium은 pretrained weight, 풍부한 레퍼런스, 빠른 실험 반복, 모델 크기 선택의 유연성을 갖고 있어 3주 프로젝트 안에서 baseline을 빠르게 구축하고 개선하기에 적합했습니다.

이 선택은 단순히 최신 모델을 사용하는 것보다, 과제 조건과 팀의 구현 가능성을 기준으로 현실적인 기술 선택을 한 결과였습니다. 이후에는 선택한 모델을 기준으로 데이터 품질 검증과 제출 파이프라인을 안정화하며 성능을 개선했습니다.
